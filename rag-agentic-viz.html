Part I

Retrieval-Augmented Generation

RAG solves a fundamental problem: language models only know what they were trained on. Their training stops at a cutoff date and never included your organization’s documents. RAG fixes this by retrieving relevant passages at question time and adding them to the prompt, so the model answers from them (Lewis et al., 2020).

Generation phase

The key insight: the model never “learned” this information. It arrives at question time, inside the prompt.

User Query

A natural-language question from the user. The model wasn’t trained on your organization’s documents, so the answer has to be looked up. Some systems first rewrite the question to search better, for example by expanding acronyms or adding details from earlier in the conversation.

Example

“How much parental leave do I get?”

Embed the Query

An embedding model converts the question into a vector: a list of hundreds to thousands of numbers that represents its meaning. The documents were converted the same way, with the same model, during ingestion, so the two can be compared.

Example

The question becomes something like [0.12, -0.84, 0.31, …], a point in a space where similar meanings sit close together.

Search

Vector search finds passages whose vectors are closest to the question’s, so it matches meaning even when the wording differs. Keyword search finds exact terms such as form numbers, product codes, and names, which vector search can miss. Many systems run both and merge the results, called hybrid search. Try it below.

Example

“Parental leave” matches a passage about “maternity and paternity benefits” by meaning. Keyword search finds the passage that mentions form HR-207.

Permission Filter

Results are limited to documents the person asking is allowed to read. Without this step, RAG can quote a confidential file to anyone who asks the right question. The filter usually runs inside the search, using access rules stored with each passage.

Example

A managers-only guide is left out for an employee, even when it’s the closest match.

Rerank

Search returns a generous set of candidates. A reranking model compares each one with the question more carefully and keeps only the best few. Sending fewer, better passages often beats sending many, because models can overlook information in the middle of a long prompt (Liu et al., 2024).

Example

Of 30 candidates, the reranker keeps 4 passages about parental leave and drops one about bereavement leave.

Augment the Prompt

The application combines instructions, the selected passages with their source labels, and the question. This is the “augmentation” in RAG. Source labels let the model cite where each fact came from. The passages are reference material, not instructions: if a document says “ignore your previous instructions,” the system should not obey it.

Example

Answer using only the sources below. If they don't
contain the answer, say so.
[1] Employee Handbook §4.2: Eligible employees receive
    16 weeks of paid parental leave…
[2] Employee Handbook §4.4: To request leave, submit
    form HR-207…
Question: How much parental leave do I get?

LLM Generation

The language model writes an answer from the passages in its prompt rather than from its training data alone. Instructions to rely only on the sources reduce made-up details but don’t eliminate them.

Example

The model combines the leave length from §4.2 with the request process from §4.4.

Response to User

The answer is returned with citations pointing to the passages it used, so the reader can verify it. If the sources don’t cover the question, a well-built system says so instead of guessing.

Example

“You’re eligible for 16 weeks of paid parental leave. Request it with form HR-207 at least 30 days ahead.” (Sources: Employee Handbook §4.2, §4.4)

How Documents Become Searchable

Before RAG can work, your documents are processed ahead of time. They’re split into chunks, converted to vectors, and stored in a search index. This is the ingestion pipeline.

  3. Embed chunksOne vector each
  4. IndexVectors, keywords, metadata

Re-run ingestion when documents change, and remove deleted files from the index, or answers will cite them.

    Key design decisions in RAG

    Too small and passages lose context. Too large and they dilute relevance and cost more tokens. Common starting points are a few hundred tokens with some overlap between neighboring chunks; tune from there with a test set of real questions.

    A common pattern is to retrieve a generous candidate set, then rerank down to a few. Sending more passages adds cost and delay, and can lower quality when key details sit in the middle of a long prompt (Liu et al., 2024).

    Hosted models are simple to start with; open models can run on your own infrastructure for cost or privacy. Public benchmarks such as MTEB (Muennighoff et al., 2023) are a starting point, but test on your own documents. Larger vectors cost more to store and search, and switching models means re-embedding everything.

    When search finds roughly relevant passages but the best one isn’t reliably near the top. A reranking model scores each candidate against the question more carefully. It adds a step, so responses take a little longer.

    Part II

    Agentic AI Applications

    An agent goes beyond Q&A: it can plan, use tools, remember, and take actions. Where RAG is a single retrieve-then-answer pipeline, an agent is a language model running in a loop that decides what to do next based on what it observes. This reason-and-act pattern is known as ReAct (Yao et al., 2023).

    The agent loops through Think → Act → Observe until it has enough information to respond, or reaches its limits.

    User Task

    A goal or complex question that takes multiple steps to complete. Unlike simple Q&A, agentic tasks often need research, reasoning, and action. A single question answered from documents usually doesn’t need an agent; RAG alone is simpler and more predictable.

    Example

    “Compare our pricing with our two main competitors and post a summary to the team channel.” This takes search, analysis, and an action.

    Guardrails

    Safety checks that surround the whole agent rather than sitting off to one side. They screen what comes in, validate every tool call, treat tool results as untrusted, pause for approval when needed, cap steps and spending, and check the result before anyone sees it. Each check can block, not just warn.

    Key techniques

    • Input screening
    • Prompt-injection detection
    • Tool-call validation
    • Output checks
    • Step and cost limits

    Input Checks

    The request is screened before the agent starts: block disallowed requests, catch attempts to override the agent’s instructions, and remove sensitive data that shouldn’t reach the model.

    Think (Planning)

    The language model reviews the task, what it has found so far, and relevant memory, then decides the next step or decides it’s finished. Planning happens here: the model breaks the task into parts and revises the plan as results come in.

    Key techniques

    • Task decomposition
    • ReAct (reason + act)
    • Self-checking and replanning

    Act

    The model requests a tool call: a structured request naming a tool and its inputs. The application, not the model, runs the tool. Each call is validated first (is this tool allowed for this task, and are the inputs safe?), and high-impact actions wait for human approval.

    Example

    search(query: "Competitor A pricing")

    Observe

    The tool’s result is added to the model’s context for the next Think step. Results are untrusted: a web page or document can contain hidden instructions aimed at the model, called prompt injection (Greshake et al., 2023). The agent should use them as information, never as commands.

    Step & Cost Limits

    A cap on steps, time, and spending for each task. Agents can repeat a failing action or wander off course; limits guarantee they stop and report what they have so far.

    Human Approval

    For actions that are hard to undo, such as sending messages, spending money, or changing records, the agent pauses until a person confirms. Teams often relax approvals for low-risk actions as an agent proves reliable. The other guardrails stay in place.

    Tool Use

    Functions the application makes available so the agent can act: searching the web, running code, querying databases, calling internal services, or posting messages. This is what makes agents more than chatbots. Give each agent only the tools and permissions its task needs.

    Key techniques

    • Structured tool calls
    • Sandboxed code execution
    • Web search
    • Database queries
    • Internal APIs

    RAG / Retrieval

    Agents use RAG to ground their reasoning in your information. The agent decides when to search and what to search for, and can search again as it learns more.

    Key techniques

    • Same pipeline as Part I
    • Agent decides when to search
    • Multiple sources
    • Reranking

    Memory

    Short-term memory is the model’s context: the task, the steps so far, and their results. Long-term memory stores facts or summaries in a database between sessions and retrieves them when relevant. Long contexts get expensive and harder to use, so agents often summarize older steps.

    Key techniques

    • Conversation context (short-term)
    • Saved facts and summaries (long-term)
    • Scratchpad for intermediate results

    Output Checks

    Before the result is shown or used: check for sensitive data, policy violations, and claims the retrieved sources don’t support. Automated evaluators, including a second model acting as a judge, can score quality, though they make mistakes too.

    Key techniques

    • Sensitive-data checks
    • Unsupported-claim detection
    • Model-as-judge evaluation

    Final Output

    The completed result, along with what supports it: the sources consulted and the actions taken. A model’s written explanation of its reasoning may not reflect what actually produced the answer (Turpin et al., 2023), so sources and actions are a sturdier basis for trust.

      Key design decisions for agents

      Start with one agent and a clear set of tools. Multi-agent systems assign specialized roles (researcher, writer, reviewer) that collaborate. They can help on large tasks, but they cost more and are much harder to debug and coordinate.

      Require approval for actions that are hard to undo, and let the agent proceed on its own for low-risk ones. Relax approvals as the agent proves reliable; keep the other guardrails in place. Most production systems start with more human oversight.

      Set limits on steps, time, and spending. Return tool errors to the model so it can adjust, and give it a way to stop and report what it has. Log every step so failures can be diagnosed.

      Frameworks speed up prototypes with ready-made tool, memory, and retrieval components, but add layers to learn and debug. A custom loop is often a short piece of code that’s easier to inspect and control. Many teams prototype with a framework and simplify for production.

      RAG or an agent: when to use which? Use RAG when the task is “answer a question using these documents,” a single retrieve-then-answer step. Use an agent when the task requires multiple steps, tool use, or actions. Many production systems combine both: an agent that uses RAG as one of its tools.

      Part III

      Design Tradeoffs

      Every decision in AI application design involves tension between competing goals. Improving accuracy often increases cost and response time, and adding safety checks adds delay. Try the settings below to see the direction of each effect.

        AutonomyThe agent takes actions on its own: faster completion, less work for people.
        ControlA person approves important actions: slower, but safer and easier to correct.

        Fully autonomous agents can make expensive mistakes. Start with approvals for actions that are hard to undo, relax them for low-risk actions as the agent proves reliable, and keep the other guardrails in place.

        FreshnessReal-time data, frequent re-indexing, live retrieval from other systems.
        ReliabilityA curated knowledge base with reviewed sources and stable results.

        Live data gives current answers but adds failure modes such as outages and unvetted content. A curated collection is more reliable but can go stale. Many systems combine a curated core with clearly labeled live sources.

        Guiding Principles

        Lessons from teams building production AI applications.

        • Start with RAG, Not Agents

          Retrieval alone solves most “the model doesn’t know X” problems, simply and reliably. Add agentic capabilities only when a task genuinely needs multiple steps or actions.

        • Evaluate Before You Optimize

          Build a test set of real questions with expected answers and sources. Check whether the right passages came back, then whether the answer is correct and supported by them. Automated judges speed this up but need spot checks by people.

        • Retrieval Sets the Ceiling

          If the right passage isn’t retrieved, no model can use it. Chunking, metadata, hybrid search, and reranking often matter more than switching models.

        • Show Sources and Actions

          Let people check answers against the passages used and see what an agent did. A model’s own explanation or confidence is a weaker signal; explanations can raise trust even in wrong answers (Bansal et al., 2021).

        • Treat Outside Text as Untrusted

          Documents, web pages, and tool results can carry instructions aimed at the model. OWASP ranks prompt injection as the top risk for LLM applications. Give agents only the tools they need and require approval for actions that are hard to undo.

        • Cost Compounds Fast

          Every model call, embedding, and search adds cost and delay, and agents multiply them. Cache repeated work, use smaller models for simple steps, and cap steps and spending per task.

        • Hallucinations Are Inevitable

          Even with good retrieval, models can state wrong details fluently, and research suggests this can’t be eliminated entirely (Xu et al., 2024). Show sources, allow verification, and avoid high-stakes autonomous decisions without human review.
